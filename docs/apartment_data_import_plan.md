# Plan: `docs/data_to_import.xlsx` import

Source spec: `docs/apartment_data_import.md`. Target: org 1 (שליחות בשיפסיידביי), local Docker Postgres only (no prod/Neon writes). Sheet: «עבודה מענדל», 27096 rows, 25141 with data (rows 2..27096, blank tail rows skipped).

Script: `backend/scripts/import_apartment_data.py`, modeled on `backend/scripts/import_data3.py` (dry-run by default, `--commit` to persist, org-scoped caches, aggregated warnings not per-row spam given the 25k row volume).

## Column reality-check (header text vs. actual content)

Row 1's literal Hebrew headers don't all match the spec's semantic labels (e.g. col C header reads "סטטוס" = "Status", col H header reads "משולב (בטא)" = "Combined (beta)") — but the **values** in every column match the spec's column-letter definitions exactly (confirmed by sampling). Column letters, not header text, are authoritative, per the spec.

## Decisions made with the user (via AskUserQuestion)

1. **Building type (Column C) → `is_town_house`.** Data-informed reading, not the spec's literal exact-match: `is_town_house = "בניין" not in Column C`. So "בניין"/"בבניין"/"מיני בניין"/"מיני בבניין" (all contain the substring "בניין") → apartment building (floors + lettered units, confirmed in the data); "בית"/"בית מחולק" → town house. Verified: all 13 addresses whose raw type string varies across rows resolve to the *same* boolean either way under this rule — no real per-address conflict remains.
2. **Apartment identity when Column G (apartment #) is blank** (8357/25141 rows, ~all בית/בית מחולק): if Column F (floor) has a value (e.g. "למעלה"/"למטה" on a divided house), use it as `apartment_name`; else (plain single house) use `"{building_display_name}-th"` — the same convention `routers/buildings.py` already uses for a town house's auto-created single unit.
3. **Duplicate rows** (431 exact repeats of (address, floor, apt) — almost all blank/blank בית pairs): merge into one apartment instead of creating a second row with the same computed name. Merge rule: first non-null wins for single-value fields (jewish_status, resident name, phone/email, report_number); notes concatenate; languages union; conflicting values on the losing row are preserved by appending to `apartment_notes` rather than silently dropped.
4. **Mezuzah notes (Column M)** — free text (e.g. `'V - טבת פ"ד'`, `'אב פ"ה - בעלה לא היה...'`, only 31/25141 rows), not a clean status; doesn't fit the existing `apartment.mezuzah_status` picklist (checked/needs_check). No field named "Mezuzah notes" exists anywhere in the app today (checked every org's `custom_field_definitions` + the frontend) — confirmed with the user this should be **created**: one new `CustomFieldDefinition` (org 1, `entity_type="apartment"`, `field_type="text"`, `field_key="mezuzah_notes"`, hebrew_label "הערות מזוזה", english_label "Mezuzah notes"), values stored via `CustomFieldValue` (`entity_table="apartments"`).

## Decisions made autonomously (documented, not asked — low-risk / clearly-correct defaults)

- **Duplicate-building prevention (found during exploration, not in the original spec):** org 1 already has 9 buildings from the `data3` import (2026-07) on Batchelder St / Avenue Z / Avenue Y, stored as `"{number} {street}"` (e.g. `"2520 Batchelder St"`). This spec's address order is `"{street} {number}"` (e.g. `"Batchelder St 2520"`). All 9 of those addresses also appear in `data_to_import.xlsx`. A literal exact-string lookup (spec Step 4) would miss the match and create 9 duplicate buildings (with duplicate floors/apartments) for buildings that already have real data (1139 existing apartments, some already linked to contacts/visits). Fix: building lookup normalizes both the existing DB address and the new row's address into `(number, street)` and matches on that, in addition to exact string match. On a match, the existing building/area is reused as-is (its `area_id` is **not** reassigned to the row's Column B code — Step 4 only sets `area_id` at creation).
- **Area (Column B)** — 216 distinct codes (e.g. "א1", "י15"), essentially all new; looked up/created by exact `area_name` match per spec. Org 1's 3 pre-existing non-"שיפסיידביי" areas ('????', 'אזור 1', 'אזור 2') are legacy/unrelated and won't collide (no Column B value matches them).
- **`apartments.floor`** is stored as the floor's *name string* (not a `floor_id` FK) — the model comment confirms floors are "referenced by apartments as free text ... so floors can be renamed freely." Resolves the spec's own "(or floor_id depending on table FK requirements)" hedge.
- **Jewish status (Column H) / Language (Column I)** → both are picklist-backed (`apartment.Jewish_status`, `apartment.language`), set via `picklist_utils.set_value` / `set_multi_values`. Values found: `גוי`, `יהודי`, `יהודי מעוניין`, `יהודי וגוי`, `יהודי מעוניין וגוי`, `יהודי שתומ"צ` all map to existing org-1 picklist options (including `gentile`, added by the prior `data3` import). A handful of messy variants (`'יהודי לא לדפוק'`, `'גוי לא לדפוק!'`, `'יהודי וגוי\nלא להגיע'`) are matched by longest-known-prefix, with the extra trailing text preserved in `apartment_notes` (mirrors `import_data3.py`'s fallback pattern). Languages split on `,`, trimmed, each mapped individually (hebrew/english/russian/yiddish) via `set_multi_values` — no need for the old combined `russian_english` value since `apartment.language` is multi-value (fixes51).
- **Resident names (Column J)** → `Apartment.name` ("שם דייר", already exists for exactly this).
- **Notes (Column K)** → `Apartment.apartment_notes`, with fallback text from unmapped Jewish-status/language/phone parsing appended.
- **Contact info (Column L, phone/email)** — reuses `app.schemas._validate_phone` / `_validate_email` (same regex the API enforces) so imported data passes the app's own validation. Email checked first (4 rows have `@`). For phone, ~97% of the ~350 non-null values are already a clean 10-digit NANP number; a handful have extra junk (parenthetical alt numbers, Hebrew asides, slash-separated second numbers) — first embedded valid 10/11-digit run is used, full raw text preserved in `apartment_notes` when nothing validates (no data silently dropped).
- **Geocoding (Step 4)** — uses the existing `app.core.geocode.geocode_address` helper (already a no-op when unconfigured). **No `GOOGLE_MAPS`/geocoding API key is set in the local backend container**, so every new building's `longitude`/`latitude` will stay `NULL` in this run — this is a pre-existing environment gap, not a script bug. If/when a key is added to `backend/.env` (`GEOCODING_API_KEY` per `app/config.py`), a follow-up pass can backfill coordinates for buildings still missing them.
- **Floor `sort_order`** — numeric floors sort naturally; letter/named floors (`B`, `L`, `PH`, `BSMT`, `למעלה`/`למטה`, etc.) get a small heuristic (basement-like → negative, `PH` → high, unrecognized → grouped fallback) since this only affects cosmetic ordering in the UI and is trivially fixable later via the existing floor reorder UI.
- **Report numbers (Column A)** — looked up/created by exact name match, independent of org 1's existing (differently-formatted) report numbers from other imports.
