# 🗄️ Database Migration: SQLite → PostgreSQL (local Docker → Neon production)

This document records the migration of the CRM from SQLite to PostgreSQL:
**local Docker Postgres** for testing, and **Neon** as the managed production
database. Most of it is already implemented — sections are marked ✅ DONE with
the actual outcome, and the original plan's bugs are corrected inline.

> Status as of this writing: local Postgres ✅, Alembic ✅, Neon provisioned +
> wiped to a clean schema ✅, production hardening ✅. Remaining: deploy the
> backend host and point it at `backend/.env.production` (set the real frontend
> domain first).

---

## Phase 1: Local Docker Postgres — ✅ DONE
`docker-compose.local-db.yml` runs an isolated Postgres 15 + pgAdmin with a
healthcheck.

```sh
docker compose -f docker-compose.local-db.yml up -d      # start
docker compose -f docker-compose.local-db.yml down       # stop
docker compose -f docker-compose.local-db.yml down -v    # reset (drops data)
```

- DB: `crm_local_dev`, user `crm_admin`, pass `local_secure_password`, port `5432`.
- pgAdmin: http://localhost:5050 (`admin@crm.local` / `admin_secret_password`).
- From the **backend container**, reach this DB via `host.docker.internal:5432`
  (not `localhost`, which is the container itself).

## Phase 2: Dependencies — ✅ DONE
`backend/Pipfile` includes `psycopg2-binary` (PG driver) and `alembic`
(migrations). After changing the Pipfile, **rebuild the image** so the running
container picks up new packages:

```sh
docker compose build backend && docker compose up -d backend
```

> ⚠️ `docker compose restart` does **not** rebuild and does **not** reload
> `env_file` changes — it reuses the env baked in at container-create time. Use
> `docker compose up -d --force-recreate backend` after editing `backend/.env`.

## Phase 3: Connection engine — ✅ DONE
`backend/app/database.py` normalizes `postgres://` → `postgresql://`, drops
`check_same_thread` for non-SQLite, and uses a pooled engine
(`pool_pre_ping`, `pool_size=10`, `max_overflow=20`). The URL comes from
`settings.database_url` (env `DATABASE_URL`).

`backend/.env` (local) currently points at local Postgres; the SQLite line is
kept commented for rollback:
```env
DATABASE_URL=postgresql://crm_admin:local_secure_password@host.docker.internal:5432/crm_local_dev
# DATABASE_URL=sqlite:///./data/crm.sqlite3
```

## Phase 4: Schema management with Alembic — ✅ DONE
We replaced ad-hoc `Base.metadata.create_all` with **Alembic** so the schema can
evolve safely in production.

- `backend/alembic/env.py` pulls the URL + `Base.metadata` from app settings
  (single source of truth), with `compare_type=True`.
- Baseline revision **`03727171e159`** ("baseline schema") creates all 23 tables.
- `backend/app/main.py` runs `alembic upgrade head` on startup (a fresh DB is
  built from migration history; an existing DB is a no-op).

Day-to-day:
```sh
# after changing models, generate a migration:
docker compose exec backend sh -c "cd /app && alembic revision --autogenerate -m 'describe change'"
# apply:
docker compose exec backend sh -c "cd /app && alembic upgrade head"
```

> Generating the *baseline* required an empty DB (autogenerate against the
> already-created local DB would produce an empty diff). We autogenerated against
> a throwaway empty database, then `alembic stamp head` on the populated one.

## Phase 5: Data migration script — ✅ DONE (corrected)
`backend/migrate_data.py` copies every row from SQLite into Postgres. The
original draft in this plan had three bugs that are fixed in the real script:

1. **`dict(row)` → `dict(row._mapping)`** — SQLAlchemy 2.x `Row` objects aren't
   directly dict-able.
2. **Sequence reset** — integer autoincrement PKs are copied with explicit ids,
   so Postgres sequences must be realigned with `setval(...)` or the next insert
   collides (duplicate key). The script does this for every serial PK.
3. **Orphaned rows** — SQLite never enforced foreign keys, so the source can hold
   rows whose FK target was deleted. Postgres rejects them. The script does a
   bulk insert, and on an integrity error falls back to row-by-row (each in a
   savepoint), dropping + reporting only the offending rows.

Run it (defaults read SQLite at `./data/crm.sqlite3`; override `POSTGRES_URL`):
```sh
docker compose exec -e POSTGRES_URL=postgresql://crm_admin:local_secure_password@host.docker.internal:5432/crm_local_dev \
  backend python migrate_data.py
```

> Our run dropped 2 orphaned `contact_picklist_values` rows (pointing at a
> deleted contact). That surfaced a real app bug — see Phase 5b.

### Phase 5b: cascade-delete bug exposed by enforced FKs — ✅ FIXED
Under SQLite, deleting a contact silently orphaned child rows. Under Postgres,
it would raise a FK violation (HTTP 500). `Contact` lacked cascades for
`visits`, `donations`, and `contact_picklist_values`. Fixed in
`backend/app/models.py` (ORM-level, no DDL change needed because deletes go
through `db.delete(contact)`):
- `visits` + `picklist_value_rows` → `cascade="all, delete-orphan"`.
- `donations` → **preserved** (financial records); their nullable `contact_id`
  is set to NULL on contact delete.
- The relationship is named `picklist_value_rows`, **not** `picklist_values`, to
  avoid shadowing the `ContactDetailOut.picklist_values` dict schema field.

Regression test: `tests/test_contacts.py::test_delete_contact_cascades_visits_and_picklists_but_keeps_donations`.

## Phase 8: Neon production database — ✅ PROVISIONED
Production DB is **Neon** (managed Postgres). Connection strings live in the
gitignored `backend/.env.production` (never commit it). `.gitignore` ignores
`.env.*` except `*.example`.

- **Pooled** URL (host contains `-pooler`) → `DATABASE_URL`, used by the app.
- **Direct** URL → `NEON_DIRECT_URL`, used for migrations / data loads.
- Both keep `?sslmode=require` (Neon also adds `channel_binding=require`).

Build / reset the Neon schema (uses the direct URL):
```sh
# build/upgrade schema:
docker compose exec backend sh -c \
  'export DATABASE_URL=$(grep "^NEON_DIRECT_URL=" /app/.env.production | cut -d= -f2-); cd /app && alembic upgrade head'

# full reset to schema-only (drops ALL data):
#   DROP SCHEMA public CASCADE; CREATE SCHEMA public;  then alembic upgrade head
```

Neon was **wiped to schema-only** for production: 23 empty tables at head. Real
organizations onboard via the public signup flow; the global localization labels
auto-seed on first boot.

## Phase 9: Production hardening — ✅ DONE
- **CORS** is env-driven via `CORS_ORIGINS` (`backend/app/config.py` →
  `settings.cors_origins_list`, wired in `main.py`). The bogus `https://vercel.app`
  origin was removed. Local defaults to `http://localhost:3001`.
- **`SECRET_KEY`** — a strong random value is set in `.env.production`.
- **`SEED_DEMO_DATA`** flag — defaults `True` locally; `.env.production` sets it
  `false` so the demo org / `admin`/`admin123` / sample contacts never reach
  production. Localization labels always seed.
