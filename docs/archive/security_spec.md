# Specification: SQL Injection Prevention & Query Validation Layer

## Objective
Implement a secure application-level gatekeeper within our Python CRM backend to intercept, validate, and sanitize raw SQL queries generated by the AI model (`claude-sonnet-5`) before they hit our database engine. This prevents Prompt Injection and unauthorized data mutations.

## Architecture Guidelines
1. **Separation of Concerns:** The AI engine writes the query string text, but our local Python environment explicitly validates and executes it.
2. **Read-Only Context:** The repository connection context manager must execute these queries using a database user account stripped of all DDL/DML mutation privileges (No DROP, DELETE, UPDATE, or INSERT).
3. **Fail-Safe Fallbacks:** Any invalid or blacklisted structure must trigger a hard security exception and pass a clean JSON error response structure back to the frontend UI layer instead of executing the database pipeline.

## Implementation Tasks

### Task 1: Create the Validation Engine (`security_gate.py`)
Create a new file or add this module inside the `ai_sandbox` directory to parse, analyze, and sanitize incoming SQL strings:

```python
# ai_sandbox/security_gate.py
import re

def validate_and_sanitize_sql(sql_query: str) -> dict:
    """
    Parses an AI-generated SQL query string against strict application security policies.
    Returns a dictionary indicating safety status, clean query string, or error messages.
    """
    if not sql_query:
        return {"is_safe": False, "error": "Empty query payload received.", "clean_query": ""}

    # 1. Uniform case processing for structural checking
    query_lower = sql_query.lower().strip()
    
    # Remove leading/trailing comments or structural code artifacts if any exist
    query_lower = re.sub(r'(^/\*.*?\*/)|(^--.*?$)', '', query_lower, flags=re.MULTILINE).strip()

    # 2. Enforcement Rule: Query MUST be a SELECT block. No multi-statement chaining.
    if not query_lower.startswith("select"):
        return {
            "is_safe": False, 
            "error": "Security Breach: Only read-only SELECT data queries are permitted.",
            "clean_query": ""
        }

    # 3. Explicit Keyword Blacklist (DDL & Write Operations)
    # Using exact word boundaries (\b) to avoid false positives on valid table/column names
    forbidden_keywords = ["drop", "delete", "update", "insert", "alter", "truncate", "grant", "replace", "create", "exec"]
    for keyword in forbidden_keywords:
        if re.search(rf"\b{keyword}\b", query_lower):
            return {
                "is_safe": False, 
                "error": f"Security Breach: Unauthorized database operation '{keyword.upper()}' detected.",
                "clean_query": ""
            }

    # 4. Enforce Row-Limit Boundary Controls (Prevent DoS Memory Blowups)
    # If the AI forgot to add a limit, we apppend a safe global ceiling natively
    clean_query = sql_query.strip()
    if "limit" not in query_lower:
        # Strip trailing semicolons if present to avoid syntax validation failure when appending
        clean_query = clean_query.rstrip(";") + " LIMIT 100;"

    return {"is_safe": True, "error": None, "clean_query": clean_query}
```

## Security review (not implemented — see rationale)

This spec was reviewed for SQL injection risk and **not implemented**. A
keyword blacklist over an AI-generated SQL string is not a substitute for
parameterization/allowlisting and has concrete gaps even on its own terms:

- No table/column allowlist: `SELECT password_hash FROM users` or a
  `UNION SELECT` pulling another organization's rows passes every check here
  (starts with SELECT, no blacklisted word) — the blacklist only stops
  *writes*, not the unauthorized *reads* that are the actual sensitive-data
  risk in a multi-tenant app. Unauthorized data disclosure via injection is
  itself a SQL-injection impact (OWASP A03), not just DDL/DML.
- The auto-appended `LIMIT 100;` is defeated by a trailing `--` comment in the
  model's query (the LIMIT lands after the comment marker and never executes)
  — the one DoS mitigation here silently no-ops.
- The comment-stripping regex only anchors at the start of the string; it
  doesn't catch structure hidden later in the query.
- The blacklist is generic/MySQL-flavored; this app's production DB is
  PostgreSQL (Neon) and the list misses Postgres-specific dangerous surface
  (`pg_sleep`, `dblink`, `COPY ... TO/FROM PROGRAM`, etc.).
- The "read-only DB user" mitigation is asserted in prose only — the sample
  code's execution line is a commented-out placeholder — and even if wired up
  it wouldn't stop the cross-tenant/credential-table reads above.

**What actually satisfies this doc's objective** (preventing SQL injection
from AI-generated queries) is already implemented: `backend/app/crm_manifest.py`
+ `backend/app/routers/ai_query.py` (`POST /api/ai/query`, see
`docs/crm_ai.md`'s amended section). The model never produces a SQL string —
it returns `{table, filters}`, validated against an explicit table/column/
operator allowlist, then built into a parameterized SQLAlchemy query with
`organization_id` + role/shliach scoping always applied by the app, never by
the model's output. That is the standard mitigation (allowlist +
parameterization) rather than a filter layered on an unsafe pattern; nothing
further is needed here.
