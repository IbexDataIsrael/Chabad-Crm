1. Goal
Let the user edit an apartment from the chat page, in the same conversation style as add-contact. This is the user's requested flow. Keep this order:
1.	Choose the "edit apartment" option in the menu.
2.	The chat asks for the address.
3.	The address goes to the CRM. If found, the CRM sends back the full address + apartment id.
4.	The chat offers which fields to edit (jewish_status, language, and any other field that the activist can edit. – note that the editable fields are controlled by admin . This is not a fixed list).
5.	The user picks a field and the system displays the picklist values for user to choose from. Only if the field is text user writes  the new value. The chat sends: apartment id + field name + new value.
6.	The server confirms. The chat shows what the server saved, read back from the server's response, not from what was sent.
2. What the CRM already has (verified facts)
The dashboard update path (backend/app/routers/apartments.py, PUT /api/apartments/{id}, function update_apartment):
•	Auth: get_current_user (user JWT). User + org come from the token, never from the request body.
•	Write permissions: a shliach can edit only apartments assigned to them (403 otherwise) and can never change the apartment number (fixes51).
•	Every value is validated against the org's picklist (validate_picklist_value) before anything is written; an invalid value means 422 and no write.
•	The write is a versioned update (_apply_versioned_update, fixes19): the current row is retired, a new row with a NEW id is inserted, editor_id is stamped with the current user, and the to_knock custom field is kept in sync on jewish_status writes (fixes71). The response is the saved apartment (ApartmentOut) with the new id.
Read and visibility rules (same file, GET /api/apartments, list_apartments): org from the token; active versions only; status="active" only, so Instinct drafts stay out of pickers; a shliach sees only the apartments assigned to them (fixes11).
Match behavior for address search (backend/app/routers/instinct/apartments.py): substring match on the building address OR the apartment number (apartment_name) OR the resident name; up to 20 results. Reuse the matching only; that router's shared-key auth is rejected in section 3.
jewish_status and language are not columns. They are org-managed picklists linked to the apartment (fixes32): jewish_status is single-value (field key apartment.Jewish_status, capital J), language is multi-value (apartment.language, fixes51). campaign_status and mezuzah_status work the same way. Current values are read with picklist_utils.get_values / get_multi_values (see _apartment_out).
Allowed options: GET /api/picklists/{field_key} returns the org's active options (backend/app/routers/picklists.py). Reads: any authenticated user in the org. Mutations: admins only.
The JWT assistant pattern exists for contacts (backend/app/routers/assistant.py, fixes113): JWT-only, user + org from the token. The new apartment endpoints mirror it.
Versioning and lineage (backend/app/models.py, class Apartment): every edit retires the row and inserts a new one with a NEW id; exactly one active (is_display=True) row per lineage. root_id chains every version to the lineage's first row. The stable lineage identity is root_id, or the row's own id when root_id is null (the root row itself). Never treat null as the identity. An apartment's full address is building_address (one string on the buildings table) + apartment_name (the apartment number) + floor.
3. Design decision (made, not open)
The chat talks to the CRM with the user's own JWT, exactly like the contact flow. New endpoints under /api/assistant/ for apartments; user + org from the token. Reads enforce the same visibility as the dashboard: the chat never discloses an apartment, address, resident, or option that the user's role could not see in the app. Writes apply the same rules and stamp the real editor.
Considered and rejected: the CRM's Instinct API (/api/instinct/apartments/*). It is guarded by a shared service key (X-Instinct-Key env, org from INSTINCT_ORG_ID) with no user identity: edits stamp editor_id NULL and the per-user rules (shliach restrictions) do not exist there. That bypasses the approved login-secured model, so the chat does not use it.
4. CRM changes (to add in sheepsidebay_crm; these endpoints do not exist yet)
1.	GET /api/assistant/apartments/search?q= (to add): JWT via get_current_user; user + org from the token. Visibility from the dashboard list rule: active versions, status="active" only (drafts stay out), a shliach sees only assigned apartments. Match behavior: substring on building address OR apartment number OR resident name, cap 20. Each result: apartment_id (the current version id), lineage_id (root_id, or the row's own id when root_id is null), building_address, apartment_name, floor, resident_name, current jewish_status, current language list (read via picklist_utils like _apartment_out).
2.	POST /api/assistant/apartments/{id}/update (to add): JWT. Body {field, value}; in this phase field is only "jewish_status" (single value string) or "language" (list of strings); any other field is a 422. Validate every value with validate_picklist_value (invalid value: 422 naming the field, nothing written). Write through _apply_versioned_update with the real current_user so editor_id is stamped and the to_knock sync keeps working. Write-side shliach rule same as the dashboard PUT (403 when not assigned). Response: the saved state, the NEW apartment_id, the previous id, and the lineage id.
3.	GET /api/assistant/apartments/by-lineage/{lineage_id} (to add): the re-resolution read. JWT; org from the token; the same visibility rules as search (active version, drafts stay out, a shliach only assigned apartments; 404 when the lineage does not exist or is not visible to this user, so existence is not disclosed). Returns the current active version of the lineage with the same fields as a search result. The capped address search is not a re-resolution route: several apartments can match one address and the cap can hide the row. Every re-resolution after a timeout or a 404/409 uses this read.
4.	Concurrency and idempotency (proposed server work; build it before the chat flow ships): the update claims the current version with a conditional write (match on id AND is_display=true), the same claim pattern the contact confirm uses, so two concurrent updates cannot both retire the same row; the loser gets 404 or 409 and the caller re-resolves. No-change rule: if the sent value equals the current value, do not create a new version; return the current state with an "unchanged" marker (the existing Instinct PATCH already treats a no-change update this way; reuse that behavior). This covers a sequential duplicate (same user, same lineage, same value sent twice in a row). It is not a race guarantee: races are handled by the conditional claim plus the client in-flight disable in section 5, not by the no-change rule. Optional later: an operation-status or idempotency-key route would let the chat resolve a timed-out update definitively; no such route exists today, so the timeout rule in section 5 keeps the edit blocked instead.
5.	Options: reuse GET /api/picklists/{field_key} (any authenticated org user may read) for apartment.Jewish_status and apartment.language. If its response shape does not fit the chat, add a thin assistant options route that reuses the same read with the same rule. The chat must show real server options, never hardcoded lists.
